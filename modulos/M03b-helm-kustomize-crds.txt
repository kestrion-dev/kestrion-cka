5.1 EL PROBLEMA QUE RESUELVE HELM
------------------------------------

```text reference
Conexion con M02 y M03: hasta ahora, cada recurso
que creaste (Deployment, Role, RoleBinding, Service)
lo aplicaste con manifiestos individuales via
kubectl apply -f. Para una aplicacion real con
decenas de recursos relacionados (Deployment,
Service, ConfigMap, Secret, RBAC, PVC), gestionar
cada YAML por separado se vuelve inviable:
```

  - No hay versionado del conjunto completo
  - No hay forma nativa de parametrizar valores
    (imagen, replicas, dominio) sin editar YAML
  - No hay un mecanismo de "deshacer" un despliegue
    completo si algo sale mal

Helm resuelve esto con tres conceptos:

```text reference
  Chart:
    Un paquete de manifiestos YAML con plantillas
    (templates) que aceptan variables. Es analogo
    a un paquete .deb o .rpm, pero para Kubernetes.

  Release:
    Una instancia instalada de un Chart en el
    cluster, con un nombre y un namespace concretos.
    El mismo Chart puede instalarse varias veces
    como releases distintos.

  Values:
    El fichero (o los flags) que parametrizan el
    Chart: imagen, tag, replicas, recursos, etc.
    Sin tocar los templates del Chart.
```

```text reference
  COMO FUNCIONA INTERNAMENTE:
    Helm renderiza los templates del Chart con los
    values proporcionados, produce YAML final, y lo
    aplica contra la API de Kubernetes (el mismo
    apiserver de siempre, Helm no es un componente
    del cluster). Guarda el estado del release
    (que se instalo y con que values) como un
    Secret en el namespace del release. Por eso
    kubectl get secrets muestra objetos con nombres
    como sh.helm.release.v1.<nombre>.v1
```

5.2 EL PROBLEMA QUE RESUELVE KUSTOMIZE
------------------------------------------

Kustomize resuelve un problema distinto: como
mantener variantes de la MISMA aplicacion (dev,
staging, produccion) sin duplicar YAML ni usar
plantillas con variables.

La filosofia es opuesta a Helm: Helm parametriza
con variables dentro de templates; Kustomize
parte de YAML plano valido (una "base") y aplica
"patches" declarativos por encima (los "overlays"),
sin tocar el YAML original.

```text reference
  Base:
    El conjunto de manifiestos comun a todos los
    entornos.

  Overlay:
    Una carpeta que referencia la base y aplica
    modificaciones: cambiar el numero de replicas,
    la imagen, agregar labels, etc.
```

```text reference
  COMO FUNCIONA INTERNAMENTE:
    kubectl tiene Kustomize integrado desde la
    version 1.14 (kubectl apply -k). No requiere
    instalar nada adicional. Lee el fichero
    kustomization.yaml de la carpeta indicada,
    combina base + overlay, y aplica el resultado.

  DIFERENCIA CLAVE PARA EL EXAMEN:
    Helm    -> kubectl NO lo entiende de forma nativa,
               se ejecuta como binario externo
    Kustomize -> kubectl SI lo entiende de forma
               nativa: kubectl apply -k <carpeta>
```

5.3 CUSTOM RESOURCE DEFINITIONS (CRDs)
------------------------------------------

Conexion con M03: en RBAC viste que Deployments
pertenecen al apiGroup "apps" y Pods al apiGroup
"" (core). Estos apiGroups no son fijos ni cerrados:
un CRD permite registrar un NUEVO tipo de recurso
en la API de Kubernetes, con su propio apiGroup,
schema y validaciones, sin modificar el codigo
fuente de Kubernetes.

  QUE ES REALMENTE UN CRD:
    Un CRD es una DEFINICION: le dice al apiserver
    "existe un recurso llamado CronTab, pertenece
    al grupo stable.example.com, tiene estos campos".
    A partir de ahi, kubectl get crontabs funciona
    exactamente igual que kubectl get pods.

  LO QUE UN CRD NO HACE POR SI SOLO:
    Un CRD por si mismo NO ejecuta ninguna accion.
    Si creas una instancia de CronTab, Kubernetes
    la guarda en etcd (como cualquier otro objeto)
    pero nadie "hace" nada con ella. Es solo
    almacenamiento estructurado con validacion de
    schema. Esta distincion es la base para entender
    los Operators en la siguiente seccion.

5.4 EL PATRON OPERATOR
-------------------------

Conexion con M01: recuerda el controller-manager
y su reconciliation loop (observar el estado
deseado, compararlo con el estado actual, actuar
para converger). Un Operator es exactamente ese
mismo patron, pero para un CRD personalizado en
lugar de un recurso nativo.

```text reference
  DEFINICION:
    Operator = CRD (el "que") + Controller (el
    "quien actua"). El controller corre como un
    Deployment normal dentro del cluster, con
    permisos RBAC sobre su CRD, y ejecuta un bucle
    infinito:

      1. Observa (watch) instancias del CRD
      2. Compara el estado deseado (definido en el
         YAML del CRD) contra el estado real del
         sistema
      3. Actua: crea, modifica o elimina recursos
         nativos (Pods, Services, Secrets) para
         converger al estado deseado
      4. Vuelve al paso 1, indefinidamente
```

  POR QUE EXISTEN:
    Encapsulan conocimiento operacional complejo.
    Ejemplo real que usaremos en el laboratorio:
    cert-manager. Sin un Operator, emitir y renovar
    certificados TLS es un proceso manual de varios
    pasos. Con cert-manager, defines UN objeto
    Certificate declarativo, y su controller se
    encarga de solicitar, renovar y almacenar el
    certificado como Secret automaticamente,
    para siempre, sin intervencion humana.

5.5 EXTENSION INTERFACES: CNI, CSI, CRI
-------------------------------------------

Conexion con M02: cuando inicializaste el cluster
con kubeadm y luego instalaste Calico, y cuando
instalaste containerd antes de kubeadm, ya usaste
estas tres interfaces sin nombrarlas formalmente.

Las tres siguen el mismo principio: Kubernetes
define un CONTRATO (una interfaz), y distintos
proveedores implementan ese contrato de forma
intercambiable. Kubernetes no sabe ni le importa
cual implementacion corre debajo.

```text reference
  CNI - Container Network Interface:
    Contrato para asignar red a los pods: IP,
    interfaces, rutas y configuracion de red.
    Implementaciones: Calico (la tuya), Flannel,
    Cilium, Weave.
    Algunas implementaciones, como Calico y Cilium,
    tambien aplican NetworkPolicy.
    Sin un CNI instalado, los nodos quedan NotReady
    indefinidamente (lo viste en M02).

  CSI - Container Storage Interface:
    Contrato para que Kubernetes pida almacenamiento
    a un backend externo (aprovisionar, montar,
    redimensionar volumenes) sin conocer los
    detalles de ese backend.
    Implementaciones: AWS EBS CSI, GCE PD CSI,
    Ceph CSI, local-path-provisioner (no es CSI
    puro, ver nota en la seccion 12).
    Se cubre en profundidad en M11 (Storage).

  CRI - Container Runtime Interface:
    Contrato entre kubelet y el runtime que
    realmente crea y destruye contenedores.
    Implementaciones: containerd (la tuya), CRI-O.
    Docker NO implementa CRI de forma nativa desde
    hace varias versiones; por eso Kubernetes usa
    containerd directamente (que originalmente era
    un componente interno de Docker).

  REGLA MENEMOTECNICA:
    N de CNI     -> Network
    S de CSI     -> Storage
    R de CRI     -> Runtime (contenedores en Ejecucion)
```

6. DIAGRAMA ASCII - OPERATOR RECONCILIATION LOOP
--------------------------------------------------

```text reference
  Usuario crea:
  apiVersion: cert-manager.io/v1
  kind: Certificate
  (instancia de un CRD)
       |
       v
  +-------------------------------------------+
  |            ETCD (via apiserver)            |
  |   guarda el objeto Certificate (deseado)   |
  +-------------------|------------------------+
                       |  watch (el controller
                       |  esta suscrito a cambios
                       |  en el CRD Certificate)
                       v
  +-------------------------------------------+
  |     CERT-MANAGER CONTROLLER (Operator)      |
  |     corre como Deployment normal            |
  |                                             |
  |   1. Detecta el nuevo objeto Certificate    |
  |   2. Estado deseado: certificado emitido    |
  |      Estado actual: no existe el Secret     |
  |   3. ACTUA:                                 |
  |      - genera CSR                           |
  |      - lo firma (self-signed o via ACME)    |
  |      - crea el Secret con el certificado    |
  |   4. Vuelve a esperar cambios (loop)        |
  +-------------------|------------------------+
                       v
              kubectl get secret
              (certificado TLS listo
               para usar en un Ingress)
```

  DIFERENCIA CLAVE CON UN CRD SIN CONTROLLER:
  Si el paso "CERT-MANAGER CONTROLLER" no existiera,
  el objeto Certificate se quedaria guardado en
  etcd para siempre, sin que nada pasara. Un CRD
  es el "que"; el controller es el "quien actua".

7.2 HELM - CREAR Y ENTENDER UN CHART PROPIO
-----------------------------------------------

Antes de usar charts de terceros, entender la
estructura interna creando uno desde cero:

```bash exec
  helm create mi-app
```

Esto genera:

```text output
  mi-app/
    Chart.yaml          metadata del chart
    values.yaml          valores por defecto
    templates/           plantillas YAML
      deployment.yaml
      service.yaml
      _helpers.tpl        funciones reutilizables
    charts/               dependencias (subcharts)
```

Ver como los templates usan variables de values.yaml:

```bash exec
  cat mi-app/templates/deployment.yaml | grep -A2 image:
```

```gotemplate template
  # replicas: {{ .Values.replicaCount }}
  # image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Renderizar sin instalar (equivalente a --dry-run):

```bash exec
  helm template mi-app-release ./mi-app
```

Instalar el release:

```bash exec
  helm install mi-app-release ./mi-app \
    --set replicaCount=3 \
    --set image.tag=1.25
```

Verificar:

```bash exec
  helm list
```
```text output
  # NAME            NAMESPACE  REVISION  STATUS
  # mi-app-release  default    1         deployed
```

```bash exec
  kubectl get deployments
```
```text output
  # mi-app-release-mi-app   3/3   3   3
```

Actualizar el release (cambiar un value):

```bash exec
  helm upgrade mi-app-release ./mi-app \
    --set replicaCount=5
```

```bash exec
  helm list
```
```text output
  # REVISION pasa a 2
```

Revertir (rollback) a la revision anterior:

```bash exec
  helm rollback mi-app-release 1
```

```bash exec
  kubectl get deployment mi-app-release-mi-app
```
```text output
  # replicas vuelve a 3
```

Ver el historial completo:

```bash exec
  helm history mi-app-release
```

7.4 KUSTOMIZE - BASE Y OVERLAYS
-----------------------------------

Crear la estructura de directorios:

```bash exec
  mkdir -p kustomize-lab/base
  mkdir -p kustomize-lab/overlays/desarrollo
  mkdir -p kustomize-lab/overlays/produccion
```

Base - Deployment comun a todos los entornos:

```bash exec
  cat > kustomize-lab/base/deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web-app
        image: nginx:1.25
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
EOF
```

Base - kustomization.yaml (indica que recursos
componen la base):

```bash exec
  cat > kustomize-lab/base/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml
EOF
```

Overlay desarrollo - solo referencia la base,
sin cambios (1 replica, imagen base):

```bash exec
  cat > kustomize-lab/overlays/desarrollo/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namePrefix: dev-
EOF
```

Overlay produccion - patch que sube replicas y
cambia la imagen, sin tocar la base:

```bash exec
  cat > kustomize-lab/overlays/produccion/patch-replicas.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 5
  template:
    spec:
      containers:
      - name: web-app
        image: nginx:1.26
EOF
```

```bash exec
  cat > kustomize-lab/overlays/produccion/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namePrefix: prod-
patches:
- path: patch-replicas.yaml
EOF
```

Ver el YAML final SIN aplicar (equivalente a --dry-run):

```bash exec
  kubectl kustomize kustomize-lab/overlays/desarrollo
  kubectl kustomize kustomize-lab/overlays/produccion
```

Aplicar cada overlay:

```bash exec
  kubectl apply -k kustomize-lab/overlays/desarrollo
  kubectl apply -k kustomize-lab/overlays/produccion
```

Verificar que son deployments independientes:

```bash exec

```
```text output

  # prod-web-app    5/5
```

```bash exec
  kubectl get deployment prod-web-app \

```
```text output

```

```bash exec
  kubectl get deployment dev-web-app \
```

7.5 CRD - CREAR UN RECURSO PERSONALIZADO SIN CONTROLLER
------------------------------------------------------------

Ejemplo clasico de la documentacion oficial de
Kubernetes, para entender la mecanica antes de
ver un CRD con controller real:

```bash exec
  kubectl apply -f - <<'EOF'
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: crontabs.stable.example.com
spec:
  group: stable.example.com
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              cronSpec:
                type: string
              image:
                type: string
              replicas:
                type: integer
  scope: Namespaced
  names:
    plural: crontabs
    singular: crontab
    kind: CronTab
    shortNames:
    - ct
EOF
```

Verificar que el nuevo tipo de recurso existe
en la API, exactamente igual que un tipo nativo:

```bash exec
  kubectl api-resources | grep crontab
```
```text output
  # crontabs   ct   stable.example.com/v1   true   CronTab
```

Crear una instancia del CRD:

```bash exec
  kubectl apply -f - <<'EOF'
apiVersion: stable.example.com/v1
kind: CronTab
metadata:
  name: mi-nueva-tarea
spec:
  cronSpec: "* * * * */5"
  image: mi-imagen-cron
  replicas: 3
EOF
```

```bash exec
  kubectl get crontabs
  kubectl get ct
```
```text output
  # mi-nueva-tarea
```

DEMOSTRACION DE LA AUSENCIA DE CONTROLLER:

```bash exec
  kubectl get pods
```
```text output
  # NINGUN pod se creo. El objeto CronTab existe
  # en etcd (kubectl get ct lo confirma) pero nadie
  # actua sobre el. Esta es la diferencia central
  # explicada en la seccion 5.3 y 5.4.
```

7.6 OPERATOR REAL - CERT-MANAGER
------------------------------------

cert-manager es un Operator ampliamente usado en
produccion. Se instala con Helm (conecta la seccion
7.2 con el patron de la seccion 5.4).

Instalar (incluye sus propios CRDs automaticamente):

```bash exec
  helm repo add jetstack https://charts.jetstack.io
  helm repo update
```

```bash exec
  helm install cert-manager jetstack/cert-manager \
    --namespace cert-manager \
    --create-namespace \
    --set crds.enabled=true
```

Verificar el controller corriendo:

```bash exec
  kubectl get pods -n cert-manager
```
```text output
  # cert-manager, cert-manager-cainjector,
  # cert-manager-webhook, todos Running
```

Verificar los CRDs que trajo el Operator:

```bash exec
  kubectl get crd | grep cert-manager.io
```
```text output
  # certificates.cert-manager.io
  # issuers.cert-manager.io
  # clusterissuers.cert-manager.io
  # (entre otros)
```

Crear un ClusterIssuer self-signed (el "emisor"
de certificados):

```bash exec
  kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: self-signed-issuer
spec:
  selfSigned: {}
EOF
```

Crear un Certificate (aqui es donde se ve el
reconciliation loop en accion):

```bash exec
  kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: demo-cert
  namespace: default
spec:
  secretName: demo-cert-tls
  issuerRef:
    name: self-signed-issuer
    kind: ClusterIssuer
  commonName: demo.local
  dnsNames:
  - demo.local
EOF
```

Observar la reconciliacion (contraste directo con
7.5, donde no pasaba nada):

```bash exec
  kubectl get certificate demo-cert
```
```text output
  # READY pasa de False a True en pocos segundos
```

```bash exec
  kubectl get secret demo-cert-tls
```
```text output
  # el Operator CREO este Secret automaticamente,
  # sin que tu lo hayas hecho manualmente
```

```bash exec
  kubectl get secret demo-cert-tls -o yaml | grep -A1 "tls.crt"
```
```text output
  # el certificado esta ahi, generado por el controller
```

Paso 4 - razonamiento de cuando usar cada uno:

  Usa Helm cuando:
    - Instalas software de terceros (ingress-nginx,
      cert-manager, prometheus)
    - Necesitas versionado de releases y rollback
    - El software tiene muchas variantes configurables

  Usa Kustomize cuando:
    - Gestionas TU PROPIA aplicacion en multiples
      entornos (dev/staging/prod)
    - Prefieres YAML plano y patches declarativos
      sobre plantillas con variables
    - No quieres una dependencia externa (Kustomize
      ya viene en kubectl)

9. CHECKPOINT
--------------------------------------------------

Pregunta 1:
  Cual es la diferencia fundamental de filosofia
  entre Helm y Kustomize?

Respuesta:
  Helm parametriza templates con variables (values)
  para generar YAML. Kustomize parte de YAML plano
  valido (base) y aplica patches declarativos por
  encima (overlays), sin variables ni templates.

Pregunta 2:
  Creaste un CRD y una instancia de el, pero
  kubectl get pods no muestra nada nuevo. Es un
  error?

Respuesta:
  No es un error. Un CRD solo define un esquema y
  permite guardar el objeto en etcd. Sin un
  controller (Operator) que observe ese CRD y actue,
  no ocurre nada mas. Es el comportamiento esperado.

Pregunta 3:
  Que dos componentes conforman un Operator?

Respuesta:
  Un CRD (define el "que": el esquema del recurso
  personalizado) y un Controller (define el "quien
  actua": el reconciliation loop que observa el CRD
  y modifica el estado real del cluster para
  converger al estado deseado).

Pregunta 4:
  Que comando usarias para ver el YAML final que
  generaria un overlay de Kustomize sin aplicarlo
  al cluster?

Respuesta:
```text reference
  kubectl kustomize <ruta-del-overlay>
```

Pregunta 5:
  Que interfaz de extension (CNI, CSI o CRI) es
  responsable de que un pod obtenga una IP al
  ser programado en un nodo?

Respuesta:
  CNI (Container Network Interface). En este
  cluster la implementa Calico.

11. TROUBLESHOOTING - CASOS REALES
--------------------------------------------------

CASO 1: helm install falla con CRDs ya existentes
-----------------------------------------------------

Sintoma:
```text output
  Error: rendered manifests contain a resource that
  already exists. Unable to continue with install:
  CustomResourceDefinition "certificates.cert-manager.io"
  in namespace "" exists and cannot be imported into
  the current release
```

Causa:
  Un intento anterior de instalacion (o una
  instalacion manual de los CRDs) dejo los CRDs
  en el cluster, pero Helm no los tiene registrados
  como parte de ningun release suyo.

Diagnostico:
```bash exec
  kubectl get crd | grep cert-manager.io
  helm list -A
```
```text reference
  # confirmar si existe algun release previo
```

Solucion:
  Si es un release huerfano, eliminar los CRDs
  manualmente antes de reinstalar (accion destructiva,
  perderia las instancias existentes):
```bash exec
    kubectl delete crd certificates.cert-manager.io \
      issuers.cert-manager.io \
      clusterissuers.cert-manager.io
```

  helm upgrade --install solo sirve si el release ya posee
  esos CRDs o si no existe conflicto de ownership. No adopta
  automaticamente recursos creados por otra instalacion.
  Antes de adoptar, verifica versiones, datos y metadatos.
  Como alternativas, gestiona los CRDs por separado o usa un
  mecanismo explicito de adopcion compatible con tu Helm.

CASO 2: el patch de Kustomize no se aplica
----------------------------------------------

Sintoma:
```text reference
  kubectl apply -k overlay no produce el cambio
  esperado (replicas siguen en el valor de la base).
```

Diagnostico:
```bash exec
  kubectl kustomize overlays/produccion
```
```text reference
  # renderizar sin aplicar y revisar visualmente
  # el YAML resultante
```

  Causa mas comun: el metadata.name del patch NO
  coincide exactamente con el metadata.name del
  recurso en la base. Kustomize empareja recursos
  por (kind + name), no por posicion en el fichero.

```bash exec
  cat overlays/produccion/patch-replicas.yaml \
    | grep name:
  cat base/deployment.yaml | grep -A1 "^metadata:"
```
```text reference
  # ambos deben decir "name: web-app" exactamente
```

Solucion:
  Corregir el name en el patch para que coincida
  con el de la base. Recordar que namePrefix se
  aplica DESPUES de emparejar, no antes.

CASO 3: certificate se queda en READY False
-----------------------------------------------

Sintoma:
```bash exec
  kubectl get certificate demo-cert
```
```text output
  # READY   False   (no cambia despues de minutos)
```

Diagnostico paso a paso:

  1. Ver el estado detallado del objeto:
```bash exec
     kubectl describe certificate demo-cert
```
```text reference
     # revisar la seccion Events y Conditions
```

  2. Ver si el CertificateRequest asociado se creo:
```text reference
     kubectl get certificaterequest
     kubectl describe certificaterequest <nombre>
```

  3. Ver logs del controller (el "cerebro" del
     Operator, aqui es donde esta la logica real):
```bash exec
     kubectl logs -n cert-manager \
       -l app.kubernetes.io/name=cert-manager \
       --tail=50
```

  4. Causas comunes:
     - El ClusterIssuer referenciado no existe o
       tiene un typo en issuerRef.name
     - El ClusterIssuer mismo no esta Ready:
```bash exec
       kubectl describe clusterissuer self-signed-issuer
```
     - El webhook de cert-manager no esta listo aun
       (tarda unos segundos tras la instalacion)

Solucion general:
  Corregir el issuerRef o esperar a que el webhook
  termine de inicializar (los pods de cert-manager
  deben estar TODOS Running, incluido el webhook).

ALTERNATIVA K3S (plan B):

```text reference
  Helm y Kustomize funcionan de forma identica en
  K3s: son herramientas de cliente independientes
  del tipo de cluster.

  Diferencia relevante: K3s incluye un controller
  propio llamado "Helm Controller", que expone un
  CRD adicional (HelmChart, apiGroup
  helm.cattle.io) para instalar charts de forma
  declarativa via manifiestos, ademas del Helm CLI
  tradicional usado en este modulo. No es parte
  del temario CKA, pero es util saber que existe
  si practicas en K3s y ves ese CRD inesperado con
  kubectl get crd.

  Sobre CSI en K3s: K3s trae por defecto el
  "local-path-provisioner" como StorageClass,
  que NO es un driver CSI real (es anterior al
  estandar CSI y usa una implementacion propia
  mas simple). Si ejecutas kubectl get csidrivers
  en K3s por defecto, tambien apareceria vacio,
  igual que en tu cluster kubeadm sin CSI instalado.
```
